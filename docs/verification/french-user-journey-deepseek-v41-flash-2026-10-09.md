第一篇采用测试自拟文本，避免借用现有用户材料：

```text
Ce matin, Léa est allée à la bibliothèque pour rendre un livre. Bien qu'il ait plu toute la nuit, elle a préféré marcher.

Le bibliothécaire lui a conseillé un roman qu'elle n'avait jamais lu.
```

```text
Après cette visite, Léa a décidé de lire chaque soir. Elle en parlera demain avec ses amis.
```

本轮发现的问题

优先级采用 P1 阻断或违背保存承诺，P2 明显影响学习功能，P3 增加操作负担。功能缺陷与产品能力缺口分别注明。

| 编号 | 优先级与性质 | 复现过程、实际结果与影响 |
|---|---|---|
| U01 | P1，取消与保存故障 | 第一篇第三句完成解析后，点击重新生成解析，随后点击取消。界面明确承诺迟到结果不会写入，但请求仍在后台成功完成，第三句持久化 revision 从 1 变成 2。重新打开第一篇并进入第三句，译文从向她推荐变为向他/她推荐，说明也变为新版本。取消既没有终止后台请求，也没有阻止写入；已有学习结果遭到覆盖。 |
| U02 | P1，结论保存故障并丢失编辑 | 第一处讨论生成回答后，点击提炼结论，改写为简短结论并确认。快捷键确认和按钮确认各试一次，均报 frenchReader/recordConclusion 请求边界校验失败。弹窗先关闭，重新打开又填入原回答，刚编辑的结论丢失；持久化讨论没有新增结论。 |
| U03 | P2，理解状态保存故障 | 同一讨论点击我已理解，报 frenchReader/setBranchState 请求边界校验失败，分支仍为 open，路线仍显示待理解。退出并重启 DSH 后再次点击，故障依旧。学习者不能完成该讨论的状态登记。 |
| U04 | P2，回答排版故障 | allée 的回答包含标题、词形表、代码标记和引用。实际阅读画面直接显示 Markdown 的星号、反引号、表格竖线与分隔行；换行合并为连续文字。性数配合表无法按行列阅读。源码 client.js:5802 直接把 message.text 放入 div，与画面一致。 |
| U05 | P2，新词学习入口缺口 | 查词输入 allée，只有本地未收藏空态，未给出原形、释义或直接新增词条的入口。随后在讨论中明确询问其原形、时态、含义和配合，回答正确并收入五条语法点，但词库仍仅有原来的 cœur、raison 两条。文案说词条随查词与讨论增长，本轮实际没有形成 aller 词条；初次使用者无法从该词继续进入动词变位卡片。这是本地查词和词条录入流程的能力缺口，不能描述为联网词典故障。 |
| U06 | P2，解析语言不一致 | 前两句的解释为中文，第三句首次解析的句法事实、语境、修辞和待查证说明几乎全部变为法语，中文用户需要额外理解法语说明。取消请求后来写入的版本又变回中文，表明输出语言没有稳定遵守中文阅读需求。 |
| U07 | P2，上下文范围不足 | 第三句给出 lui 与 elle 是否同指待查证，取消后写入的版本还译为他/她。上一自然段已经引入 Léa，整篇叙事连续，但单句解析只发送当前自然段，第三句所在段落恰好仅有这一句。controller.ts:2791 与 analysis-store.ts:159 的提示词构造确认没有纳入前段。单句内保留不确定性合理，产品没有给解析提供跨段指代所需的已录入材料。 |
| U08 | P2，讨论生成反馈不足 | 发送讨论后，发送按钮及模型选择禁用，问题仍留在输入框；本次约 17 秒内没有观察到清晰的生成用时、取消入口或逐步出现的回答。完成后回答位于另一滚动区域，用户仍需滚动才能发现。此项描述本次可见行为，不据此断言所有路由都没有流式能力。 |
| U09 | P3，阅读空间与滚动负担 | 应用侧栏、书籍目录、长书名和段落标题、原文区域及工具栏持续占据大量空间。讨论内容和输入区有不同的滚动区域，在输入框附近滚动不能直接查看完整回答，需要在回答区域内另行滚动。回答完成后没有清晰地把新内容带到当前视野；展开原文后这一问题更明显。大窗口也出现此负担。 |
| U10 | P3，初次录入预览不完整 | 预览正确报告两个自然段三句，但按段显示摘要，第一段末尾有省略，没有逐句展示边界。展开预览后确认保存按钮移出当前可见区域，需要额外滚动。初次用户难以在一个画面中同时检查切分和完成保存。 |
| U11 | P3，讨论入口增加步骤 | 加讨论先要求创建有标题的新分支，创建后仍停留在句子解析，必须再点击新分支才看到提问区。从已有回答分叉也没有自动进入新分支。即时询问一个词形需要先处理组织结构；新分支这一术语也比讨论更偏实现。 |
| U12 | P3，阅读位置不恢复 | 退出精读面板后再进入，先回到目录起始页；重新打开第一篇回到第一句。应用退出重启后也如此。原文、解析、分支、章节与下一段连接都保存了，但当前句子位置没有恢复，持续阅读需要重新寻找位置。所选 DeepSeek 模型在重启后保持，不能把模型偏好也归为丢失。 |
| U13 | P3，历史上下文回看不足 | 重启后打开已回答讨论，展开本次上下文，显示尚未编译上下文。持久化回答实际带有 contextId，对应 contextManifest 文件也存在。输入新问题再点击查看本次上下文才能获得新一轮材料和提示词；这不能代替回看原回答所用材料。 |
| U14 | P3，错误提示与状态表达 | 保存结论、理解状态的本地操作错误都统称生成功能不可用，并暴露 typert gateway、wire field、boundary validation 等内部术语，没有说明保留了什么、如何恢复。查词空态重复显示未收藏。路线中的章节名显示章节 1，没有使用已经录入的 Une visite à la bibliothèque。 |
| U15 | P3，未接入功能占据阅读界面 | 发音按钮禁用，路线中每句还显示重新生成发音及接口预留。没有把这些项目当作已经可用的发音功能，也没有尝试调用不存在的音频服务；它们持续出现在普通阅读路径，增加无效控件。 |

处理速度调查

以下时间来自本轮真实 job 记录，均为所选官方 DeepSeek 路由。首个文本指后台收到第一份非空 text-delta，不等于界面已经显示内容。输出 tokens 按供应商返回的 usage 原值记录，不能全部解释为最终可见文字，也不能据此计算纯正文输出速度。

正常解析的平均总用时约 50.6 秒。模型调用几乎占全部时间，解析校验及保存等可测差额约 21–23 毫秒，因此本轮的主要延迟不在保存或前端页面渲染。三个正常解析中，等待首个文本占模型调用约 85.5%–92.0%；文本开始后约 4.6–6.3 秒完成。讨论同样主要耗时在首个文本之前。

这些数字能够确定等待集中在模型调用开始到首个正文之间，但不能继续区分供应商排队、网络握手、内部推理或宿主对正文的缓冲。job 没有这些阶段的独立时间，也没有供应商内部推理明细。分析任务的 usage 输出高达约 1.2–1.5 万 tokens，值得进一步核查供应商统计与推理设置，但本轮不把它当作已经证实的原因。相较此前其他路由的数分钟，本轮确实更快；不能把跨模型、跨时间的样本差异视作严格性能对照。

用户体验还有独立于供应商耗时的问题：讨论等待期缺少明确反馈，取消承诺与实际保存相反。即使模型响应进一步加快，这两项也不会自动消失。
