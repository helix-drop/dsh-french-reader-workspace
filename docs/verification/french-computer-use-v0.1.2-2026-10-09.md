## 生成速度调查

本次慢主要发生在模型调用期间。当前解析任务未指定推理等级，继承了 Xiaomi 路由的 high 推理设置；模型适配器把推理 token 合并进 outputTokens，而插件不处理 reasoning-delta。读者因此长时间只看到等待计时，无法判断模型正在推理还是连接停滞。这个配置与计数事实已经确认，但现有记录不足以精确分解服务端排队、首 token 等待、推理和正文生成各自占用多少秒。

| 证据 | 实测或读取结果 | 能说明的范围 |
|---|---|---|
| 本次完整解析 | 输入 699 token，输出 13,459 token，回复正文 6,314 字符，耗时 217.029 秒 | 总输出远大于读者最终看到的正文；outputTokens 含推理，不能直接当作 JSON 正文 token 数 |
| 同一路由旧解析 | 227.890 秒 / 8,421 输出 token；228.825 秒 / 8,909；289.424 秒 / 7,137 | 3 至 5 分钟现象有多条任务记录支持，不是本次偶发的前端等待 |
| 同一路由短问答 | 9.541 秒，输入 486、输出 328 token，成功 | 同一路由可以快速完成较短任务；不能把所有慢调用归因于网络本身 |
| 推理配置继承 | 插件传 reasoningEffort: null；控制器转成未指定；安装包适配器使用 options.reasoningEffort ?? profile.reasoning；当前 Xiaomi 配置为 high | 解析实际采用默认高推理配置，而不是任务明确选择较低推理等级 |
| 输出统计与界面反馈 | 安装包适配器注明推理合并到输出计数；适配器提供 reasoning-delta，插件生成层只处理 text-delta、usage、finish | 当前统计没有单独列出推理消耗，界面也没有显示推理进展 |
| 本地重放同一回复 | JSON 解析 2.639 毫秒，结构校验 0.603 毫秒，均成功 | 本地解析和结构校验合计约 3.24 毫秒，不是本次几分钟延迟的主要来源；此测量未覆盖实时网络与完整存储耗时 |
| 解析提示词要求 | 模型需要输出完整结构、精确字符范围、逐词覆盖、从句范围以及多类解释 | 相比短问答，任务输出与精确索引计算更复杂；这对推理耗时的贡献属于合理推断，尚无对照实验 |
| 超时调整 | 客户端预算 600 秒 | 可以容纳本次 217 秒的成功调用；单纯加长预算不会提高生成速度 |

13,459 / 217.029 约为 62 个输出 token/秒，这是整个请求时长的平均比值，不能据此确定模型实际解码速度。记录的 streaming 阶段在进入 provider 流循环前设置，也不能用它当作收到首 token 的时间证据。

若后续考虑提速，优先值得比较同一句在明确指定低或中推理等级时的耗时与覆盖质量，再考虑把字符位置计算改为本地确定性处理。当前没有进行这些配置或代码修改，也没有承诺降低推理等级后一定维持解析质量。
